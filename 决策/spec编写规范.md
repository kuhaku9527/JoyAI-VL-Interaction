# spec 编写规范（决策捕获式）

> 定位：L4 治理条目（方法论铁律）。与 `跨域铁律.md`、`AI代码质量约法三章.md` 同级，由审查组维护。
> 关联模板：`doc/specs/_SPEC-TEMPLATE.md`（各端点写 spec 时套用）。
> `modified: 2026-08-06｜by AI（审查组）｜approved: 用户`

## 0. 缘起：为什么要有这条规范

`决策/` 目录是「严重偏移后迫不得已」的补救品——根因是 **spec 没有随开发同步写，AI 跑得太快，决策态与代码态失联**。补救靠事后补 `决策/`，成本高、且易再次漂移。

本规范把 spec 重置为**随开发同步的主动决策捕获**，从源头减少对 `决策/` 补救的依赖。

## 1. 分工定义（spec vs 决策/）

- **spec（`doc/specs/*.md`）= 随开发同步写的主动决策捕获**。开发过程中同步起草、修订、定稿，承载「为什么这样选」与「不能怎么做」。
  - 强制带**生命周期标记**：`草稿` / `修订中` / `正式`，体现 draft→formal 同步流。
- **`决策/` = 偏移发生后的应急回收 SSOT + 跨域治理**。继续存在，但定位从「主捕获」退为「应急 + 治理」，由审查组独占写。
- **默认 spec-first**：日常决策记进 spec；只有当 spec 已漂移、需要回收对齐时，才落 `决策/`。

## 2. spec 四要素（强制）

1. **因果链（Why / Why-this-choice）**：开篇写清「为什么这样选、为什么是这个范式」。必须包含**被否方案及理由**——这既是论证，也是负面约束的因。
2. **条件性 harness**：仅当满足以下任一才写 `Harness` 段，否则不写（避免 spec 臃肿）：
   - 该 spec 的实现/验证涉及一个**跨 ≥2 任务或 ≥2 agent 复用**的流程；或
   - 是一个**必须被原样复现的仪式**（如 drift-gate 跑批、golden-recall 封闭回路、发布验证）。
   - harness 段写清：可复现工作流 / 命令 / 验证仪式，使任何人接手都能原样复现。
3. **负面约束（What NOT to do）**：在因果链内作为补充，写「不能做什么、为什么不选替代方案」。不是孤立清单，而是因果链的自然延伸。
4. **生命周期标记**：`草稿 / 修订中 / 正式`，标明当前同步状态。

## 3. 排除项（明确禁令）

以下**不进 spec**，按其性质路由：

- **bug 修复 / bug 验证 / 运维操作** → 归 runbook（`docs/github-runbook.md`、`services/memory-store/tools/README.md` 等）或 `决策/` 回收。
- spec 只记「**有价值的决定**」——即 AI 开发速度与需求摩擦中敲定、且未来会被反推误读的决策。
- 反例：不要为「某次 bug 的修复步骤」「验证某接口是否通」写 spec；那是 runbook / 验证清单的活。

## 4. 与模板、治理的关系

- 套用 `doc/specs/_SPEC-TEMPLATE.md` 起手，确保四要素齐全。
- 本规范是 `决策/` 的**上游纪律**：spec-first 减少未来 `决策/` 补救的需求，但不取代 `决策/` 的应急 / 治理角色。
- 既有范例：`doc/specs/drift-gate-harness-spec.md` 已符合本规范（§1 因果链、§2 铁律-with-why、§3 负面约束、§4 harness）；新 spec 应对齐此范例。

## 5. 审查组职责

- 本规范由审查组维护（与 `跨域铁律.md`、`AI代码质量约法三章.md` 同级）。
- 各端点写 spec 时，审查组做合规抽查：四要素是否齐全、是否误把 bug 修复写进 spec、harness 是否满足条件。
